Permission is checked in the Brain API on every request, using four inputs: role (Executive / Privileged / Regular), client scope (which clients the person works on), workflow scope (the recruitment front end never reads finance, for example) and the sensitivity label on each row. Short answer: you don't need to settle every idea now.

The architecture has five sockets. Almost any new idea plugs into one or more of them without changing the core:

SocketWhat plugs inWhat it costs to add one
Source → collectorany new stream of informationone collector that writes events (and media refs) with a stable upstream id
Workflow (agent job)anything that reads events and produces somethingone job on the queue, with its own findings file and eval cases
Front endany new screen, bot, app or hotkeyan API client plus a tile and a role rule
Outbound connectorpushing results into another system (TimeCamp, Asana, email)one writer behind the API's human-approval rule
Media tiernew kinds of files and how long to keep thema lifecycle rule (holding → hot → cold → delete)

Four things are expensive to change later, so they should be right in Phase 2 even before every idea is known:

  1. The event schema. Every event records who did it, when it happened, when we learned of it, through which channel, about which entities, plus a sensitivity label and source links. Get this generic and every new source fits.
  2. Identity and permissions. Role × client × workflow × label, checked in the API. Adding front ends or roles is then config.
  3. Consent and ownership of personal capture. Data a person captures about themselves (screen, phone, WhatsApp) is theirs first, private by default, and released by them.
  4. Media lifecycle. Video and images get a tier and an expiry from day one, so storage costs stay predictable as capture grows.

What would force an architecture change: needing sub-second real-time behaviour everywhere (the design is minutes, not milliseconds); letting clients log in (that's multi-tenant auth, a bigger step); or holding regulated health data, which SSG does not have (confirmed 11/26). Speed: you need urgent items such as Nik's instructions in under 5 minutes; that fits, with webhooks or 1–3 minute polling for the urgent sources and an event-triggered job for each. Today the gap is the WhatsApp collector, which runs hourly. Clients logging in means outside people (Isaac, a candidate, a recruiter) having their own accounts to open a client page or player. Expiring share links don't need that; real accounts for outsiders do, and that's the bigger step.

Idea: a Bluey-style screen companion (Windows)

What Bluey actually is

A Mac menu-bar app and an iPhone app, written in Swift and released under the Unlicense (public domain), so anything can be reused. During a focus session it screenshots the main display every 30 s, sends a reduced JPEG plus the stated task to OpenAI, and nudges when you drift off task. It also has a point-and-ask cursor and voice input. It is a focus tool, not a recorder. It keeps no history of your day, and there is no Windows version, so for SSG it's a design reference, not code we can run.

Verdict: it fits without changing the architecture

It touches four sockets: a new source (screen activity), new workflows (time assembly, clip routing), new front ends (snip and ask, the clip hotkey) and an outbound connector (TimeCamp). It becomes part of the SSG Capture desktop app already planned in Phase 6 (BrainCapture), not a separate product.

Idea: a temporal knowledge base, at company, team and person level

Today it only half happens. The raw ledgers, _brain-events.jsonl and the Timeline/ pages are in time order, and the pages are dated. But the synthesis is prose per subject, so "what happened, in what order, through which channel, across the company" can only be answered by an agent reading several pages and reassembling them. It also mixes up when something happened with when we captured it: the WhatsApp voice-note dating bug is exactly that.

In the target design it is the spine, not a feature. Every item becomes an event row carrying actor, channel, entities, occurred_at (when it happened) and recorded_at (when we learned of it). Facts carry valid_from / valid_to, so we can also ask what we believed on a given date. With that in place:

  • Company level: all events in order, filterable by channel.
  • Team or client level: the same, filtered by entity or client.
  • Person level: filtered by actor. Time tracking is this view turned into blocks.
  • Episodes: one job groups related events from different channels into one happening. The Zoom call, the WhatsApp right after it and the follow-up email become "Nik and Jeff settle the HR role, 11/24".

These are queries, not separate systems. This is the one design point I'd add to Phase 2: make events bi-temporal and channel-aware from the first table. The board listed Graphiti as "probably skip"; that's still right, because Postgres covers it if the columns exist from the start.
